# Implementation plan: v0.9.1 reader-friendly guides

## Goal

Make the shortest path obvious for a tired or first-time programmer while
keeping advanced release and architecture material available. Free Pascal is
the primary example, but the writing advice must work for any code project that
can keep Markdown in a repository.

## Slice 1: A calm first success

1. Replace the long, repetitive README with a short project overview, a
   copyable local-preview path and clear links for the next goal.
2. Rewrite the documentation home and beginner guide around visible outcomes,
   plain language, expected results and safe stopping points.

**Acceptance criteria**

- A new reader can find the first successful local preview without reading
  release concepts.
- Pascal-specific scope and language-independent use are both stated plainly.
- Commands identify where to run them and what success looks like.

## Slice 2: Teach documentation, not only the tool

3. Add a language-neutral guide for planning and writing useful code
   documentation, with a copyable page template and review checklist.
4. Add a small glossary for unavoidable documentation, Git and publishing
   terms.
5. Reorder navigation so learning, writing and customisation come before
   release operations and project internals.
6. Record the reader-first documentation policy in the existing ADR series.

**Acceptance criteria**

- A 16-year-old reader can use the writing guide without knowing Pascal.
- New terms are defined close to first use or linked to the glossary.
- Maintainer-only pages do not interrupt the beginner journey.

## Slice 3: Low-stress publishing

7. Add a simple mode chooser and complete copyable workflows to the GitHub
   Pages guide.
8. Rewrite the pre-publish checklist as exact ordered steps with expected
   results and recovery guidance.
9. Clarify historical-release guidance and example READMEs without weakening
   immutable release safety.

**Acceptance criteria**

- Readers can choose single-version or historical publishing in under a
  minute.
- Each path provides a complete workflow and an exact local verification path.
- Safety terms such as tag, `HEAD`, immutable and source ref are explained.

## Slice 4: Release preparation and review

10. Update release pins, package metadata, changelog and version manifest to
    v0.9.1.
11. Run the documentation check, complete test suite, release-candidate builds,
    real-browser checks and five-axis review.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Simplifying removes useful detail | Keep advanced pages and link to them from short summaries. |
| Friendly prose becomes vague | Pair every task with exact files, commands and expected results. |
| Publishing examples drift | Test release pins and validate the generated documentation site. |
| General advice obscures Pascal focus | Use Pascal examples while explicitly marking reusable principles. |
