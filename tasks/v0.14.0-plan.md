# Implementation plan: v0.14.0 — GitHub in One Command

## Overview

Add `dockit-fp github-pages` as the safe, offline setup path for an existing
Git repository. It reuses the existing conservative `init` path, generates one
small managed caller workflow, validates the resulting documentation, and
leaves committing, pushing, repository settings and GitHub authentication to
the maintainer.

## Architecture decisions

- Generate only `.github/workflows/dockit-pages.yml`; it calls the existing
  reusable Pages workflow pinned to the running DocKit release.
- Use a stable DocKit marker and deterministic template rather than a YAML
  dependency. A recognised managed workflow can be checked exactly; a malformed
  or unmanaged file is never overwritten.
- Trigger on pushes but gate the job to GitHub's repository default branch via
  event metadata, avoiding a hard-coded branch name and preventing deployment
  from feature branches. Manual runs are gated the same way.
- Use `init` directly for first-time configuration and pre-validate existing
  partial/invalid configuration before making changes.

## Risks

| Risk | Mitigation |
| --- | --- |
| Overwriting maintainer workflow | Refuse files without the exact managed marker; require `--update` for old managed content. |
| Deploying a feature branch | Gate the reusable-workflow job to the repository default branch. |
| New setup diverges from init | Invoke the existing `_init` function rather than duplicating discovery. |
| Self-hosted workflow circularity | Keep DocKit's historical release workflow local; test the generated caller fixture before the v0.14 tag exists. |
